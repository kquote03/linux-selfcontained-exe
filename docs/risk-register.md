# Risk register

| Risk | Status | Notes |
|---|---|---|
| RVVM's NVMe/RTL8169 device model may not be reachable by a stock Debian riscv64 kernel/initramfs | **Resolved — confirmed working** | Phase 0 spike (`docs/phase0-spike-results.md`) confirmed both drivers bind cleanly with a completely stock modular kernel+initramfs pair, booted via the normal `fw_payload.bin` (OpenSBI+U-Boot) + extlinux path. No custom kernel build needed. |
| RVVM's exact `-k`/initrd/cmdline flag semantics for direct kernel boot | **Moot for this project** | This concern only applies to the bare `-k` direct-kernel-payload path, which this project doesn't use. The project boots a fully-installed OS via `fw_payload.bin` + U-Boot + extlinux, which loads the initrd itself exactly like GRUB would — RVVM's CLI never needs to know about it. Confirmed working in Phase 0. |
| RVVM has no pinned stable release; v0.6 is explicitly marked superseded by the maintainer | **Accepted, mitigated** | Use a specific nightly CI artifact, pinned by commit hash in `packaging/payload-manifest.json` (Phase 0 used `v0.7-git-gce8ca7c`). Never track "latest". |
| RVVM is a small, largely one-maintainer project with thin docs | **Accepted, de-risked by Phase 0** | Phase 0 spike confirmed boot, storage, network, display, and HID all work out of the box with no workarounds needed. QEMU remains a documented fallback (see `docs/architecture.md` "Fallback seam") if problems surface later in the full XFCE build, but is no longer considered likely to be needed. |
| RVVM's console/UART cannot be driven via redirected stdin/pipe — only real GUI window keyboard focus works | **Known, not a blocker** | Confirmed in Phase 0: this is how RVVM works by design (same as any normal desktop app), not a bug. Affects only how *this project's own automated tests* must be written (drive the GUI window via UI automation, not piped stdin) — has no effect on real student usage. |
| Debian's stock riscv64 kernel lacks `CONFIG_FB_SIMPLE`/`CONFIG_DRM_SIMPLEDRM`, so Linux never takes over the display U-Boot hands off — GUI window freezes showing only U-Boot's last frame | **Resolved — confirmed working** | Root-caused via kernel `.config` inspection (see `docs/phase1-evidence/`). Fixed by cross-compiling a custom kernel (same 6.12.111 version as Debian's, same `.config` as a base) with `CONFIG_DRM_SIMPLEDRM=y` + `CONFIG_SYSFB_SIMPLEFB=y` built in. Confirmed: full XFCE4 desktop renders correctly, autologin as `student` works. See `docs/phase1-spike-results.md`. |
| Custom kernel build pulls in Debian's full "broad hardware support" driver set (amdgpu, all NIC vendors, legacy SCSI/FC, wireless stack, hundreds of TV/webcam drivers), making cross-compile very slow | **Mitigated** | Trimmed `CONFIG_DRM_AMDGPU/RADEON/NOUVEAU/I915`, all `CONFIG_NET_VENDOR_*` except `REALTEK`, and `CONFIG_SCSI_LOWLEVEL`/`CONFIG_MAC80211`/`CONFIG_WLAN`/`CONFIG_RDS`/`CONFIG_INFINIBAND`/`CONFIG_ATM`. Full build still includes many unneeded-but-harmless modules (media/TV drivers etc.) — further trimming is a future optimization, not a blocker, since the build only needs to happen once per kernel-config change. |
| Custom kernel was missing the driver for RVVM's actual keyboard/mouse device — initially misdiagnosed as a missing Goldfish driver, actually a missing `CONFIG_I2C_HID_OF` | **Resolved** | First hypothesis (enabling `CONFIG_KEYBOARD_GOLDFISH_EVENTS`, on the assumption RVVM's input follows the same "Goldfish" device family as `goldfish_rtc`) was wrong and didn't fix anything — confirmed by dumping RVVM's actual device tree (`rvvm -dumpdtb`), which shows no Goldfish input node at all. RVVM instead exposes keyboard/mouse as three `hid-over-i2c` devices on an OpenCores I2C controller (`compatible = "opencores,i2c-ocores"`). The real fix: enable `CONFIG_I2C_OCORES`, `CONFIG_HID`, `CONFIG_HID_GENERIC`, `CONFIG_I2C_HID`, and critically `CONFIG_I2C_HID_OF` (the device-tree glue driver — distinct from `CONFIG_I2C_HID_ACPI`, which doesn't apply here since ACPI is disabled), all built-in. Verified at the kernel level (dmesg shows `hid-generic ...: I2C HID v1.00 Mouse`/`Keyboard` binding for all three devices) and via UI automation (mouse click/double-click, `Alt+F2` app finder, typed text, launched a terminal — all screenshotted in `docs/phase2-evidence/`). See `docs/phase2-spike-results.md`. |
| Full XFCE4 desktop performance under pure software CPU emulation on genuinely weak host hardware | **Mitigated, tuned against real hardware data** | Display and input confirmed working (Round 2); Round 3 tuned against a guessed hardware profile. Round 4 replaced that guess with a real CPU-Z report from an actual target machine (Xen HVM domU, 2 fixed-frequency Broadwell-EP cores, ~6GB RAM, non-accelerated Cirrus Logic VGA, ~12GB free disk) and re-tuned accordingly: disk image shrunk 8GB→4GB (matches measured ~2.2GB rootfs usage, cuts per-launch decompression/disk-write time), resolution default dropped to 800x600 (fewer pixels for the non-accelerated display chain, visually confirmed no layout breakage), RAM default re-confirmed at 1G with evidence (zram shows 0B used at idle, so there's no swap pressure to relieve by raising it), and a CPU-targeted RVVM self-build (AVX2/FMA3/AES, explicitly not BMI1/BMI2 since the real target machine's hypervisor masks those) was added, auto-selected at runtime by CPU-feature detection so it can never run on an incompatible machine — measured ~3% CPU-time reduction in a controlled A/B test. See `docs/phase4-spike-results.md`. **Still unmeasured: actual speedup magnitude on the real target machine itself** — every change this round was verified for correctness on dev hardware, not the Xen HVM target profile, so the next real confirmation needs the user's own hands-on test on the actual targets. |
| Guest sshd is not enabled by default on generic test images (confirmed on the Arch RISC-V test image used for Phase 0) | **Noted** | Not a problem for this project's scope (no inbound SSH access is planned by default — see `docs/architecture.md`), but worth remembering if SSH-into-guest is ever added as an instructor-opt-in feature: the guest image build must explicitly enable `sshd.service`. |
| Unsigned multi-GB exe triggers Windows SmartScreen; RVVM's usermode networking may trigger a Windows Firewall prompt | **Accepted** | Out of scope to code-sign for now. Document for instructors as an expected click-through. |
| Large binary assets (disk image, RVVM binary, kernel, firmware) must not bloat the git repo | **Mitigated** | Never committed; `.gitignore`'d. Rebuilt deterministically from `packaging/payload-manifest.json` (pinned URLs + SHA256) via `fetch-*.sh` scripts. |
| RVVM's stock Win32 GUI backend only supports a fixed-size, non-resizable window (confirmed via source inspection: no `WS_THICKFRAME`, and the draw path is a 1:1-only blit with no scaling) | **Resolved** | Round 5: patched `src/gui/win32_window.c` (`image-build/patches/0001-win32-resizable-scaled-window.patch`) to add resizable/maximizable window styles, an aspect-ratio-preserving letterboxed scaled draw path (`StretchDIBits`), and matching mouse-coordinate remapping (without which resizing would silently break all click accuracy). Both shipped RVVM variants now self-built from this patched source via `image-build/build-rvvm.sh`. Verified by direct boots: native size unchanged, scale-up and scale-down (with correct letterboxing) both confirmed, and mouse-click accuracy confirmed correct at a scaled size. See `docs/phase5-spike-results.md`. |
